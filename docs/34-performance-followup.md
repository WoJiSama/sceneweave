# 性能优化后续记录

初始记录：2026-10-23，C5批次版本`0.2.0-m1-c5`。2026-10-24用户单独授权修复当前原生完整v1的样板加载，结果见本文末节；其余领域/保存/恢复优化和正式矩阵继续后置。本记录不改变格式、容量承诺或验收门槛。

## 排期决定

用户在资源复用第一批完成后要求提交推送现有成果，并将后续性能优化暂时记录，等其他需求做完再继续，以便在功能路径稳定后统一处理新出现的问题。

因此暂停新的性能专项优化和正式矩阵补测，性能欠项暂不阻塞后续需求开发；M1-D及后续需求按[路线图](07-roadmap.md)与实际任务授权推进。本轮仅提交和记录，不开始新的功能切片。C5整体、完整M1和QA-PERF-01/04仍未通过，开发排期调整不能记为性能验收完成。后续功能的正确性、完整存档、迁移、玩家隐私、失败保护与适用回归继续执行。

## 恢复工作入口

其他需求完成后，先核对届时的实现与负载，从新的正常生产构建建立基线。33的300多毫秒领域提交和秒级保存仅定位到完成边界，尚无新的CPU分段证据能断言剩余成本占比。

1. 分段记录prepare、命令apply、materialize、依赖/玩家投影，以及save、原件捕获、保护点和CAS，区分领域提交、画布就绪、保存与显示代理。
2. 根据实际热点评估局部验证/依赖索引、保存与原件复用或渲染资源路径；保留资源/许可闭包、锁、256展开预算、单调revision、保护点、同事务CAS和秘密过滤。
3. 每批优化做适用正确性回归和同方法诊断；稳定后串行执行独立完整四组×三轮正式矩阵，报告样本数、各轮差异、nearest-rank p95及资源观测局限。

正式方法与命令见[贡献说明](../CONTRIBUTING.md)，通过条件仍以[质量计划](09-quality-plan.md)为准。新测量使用新目录，保留32/33和全部旧证据，不把暂停写成解决，也不预设换引擎、Worker或新缓存一定有效。

## 2026-10-24：原生完整v1样板加载修复

用户明确授权修复“点击样板到确认打开之间等待”的问题。当前默认路径已由M2-0f切到原生完整v1，旧v2→v3的ZIP压缩/解压迁移往返不在这条链上；本次定位到逐张读取资源、已经验证的结果在应用交接中再次全验，以及打开工程即后台读取57张内置目录图片。没有证据将主线程工作归因于GitHub Pages服务器算力。

- 固定资源改为最多4个并行字节读取，保持声明/实际长度、累计字节与像素预算及后续完整hash/图片/派生像素校验。任一失败停止队列、取消在途读取并等待收尾，不返回半套工程；不并行增加像素解码槽。
- 仅复用校验器自有不可变数据及字节闭包的真实凭证，应用包装另由私有WeakMap识别；换数据、端口、克隆或伪冻结不能继承证明。冷仓库先完整验证再交接，公开验证、保存、导入/导出与渲染继续全验。
- 内置62项目录改为显式打开“内置素材”或分步制作确实需要时才读取；同会话共享一次准备，失败可重试。新建/打开工程不再顺带读取整套目录，已有预装内容不变。
- 点击后先绘制“准备打开工程”窗口，再做准备；显示实际图片读取数量，完整验证阶段使用不定进度。取消等待资源收尾，当前工程/撤销保持；仅完整成功并复查会话基线后提供确认候选。
