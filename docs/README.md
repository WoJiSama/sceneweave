## 文档编号与开发阶段的关系

01–12按主题说明产品需求、交互、实现方案、验收和依据；文档编号用于查找，不表示开发先后。一项功能通常同时涉及多份文档，例如玩家秘密保护由01定义需求、04定义可见性数据、06规定导出、09规定测试，再由07安排实施。14–16补充视觉规范、素材制作与设计交接；13及17–22保存各批次的实际验证记录。

M0–M4是同一个Sceneweave产品逐步累积能力的开发阶段：M0验证技术基础，M1完成室内、室外与混合地图的手工创作，M2增加使用已有素材的AI初稿与布景，M3进行三类真实小团验证，M4适配首个VTT目标。后续阶段沿用并回归前面已实现的能力，具体任务和退出条件统一见[07路线图](07-roadmap.md)。

M1-A/B/C/D是M1内部的子阶段；B1–B5是M1-B的交付批次，C0–C5是M1-C的实施切片。当前B5技术测量已有历史交付，C0性能与视口基础已实现，验证和测量由22记录，后续开发入口为C1；这不表示整个M1已完成，后续安排见[滚动周计划](07-roadmap.md#43-b5-后的-m1-c-滚动周计划)。周次为尚未确认的投入占位，不是C0已发生工时或M1完成日期。

M1–M4覆盖[01](01-product.md)定义的核心产品路线。AI生成新的组件、变体和材质另列为M2之后的可选A1，独立安排且不阻塞M3/M4；M2仅使用已入库素材生成结构与布景。3D、多楼层联动和多人实时协作等[当前非目标](01-product.md#24-当前非目标)未纳入这条路线，不能视为已排期功能。

## 主定义原则

对象字段以04为主定义，存储/导出以06为主，AI协议以05为主，视觉规范以14为主，素材制作清单以15为主，阶段/排期以07为主，样板内容以08为主，QA定义以09为主，16记录本批交接且不重复主定义。发现不一致时一起修订，不能据“优先级”忽略实际矛盾。产品范围变化先改01与11，再调整实现/验收契约。

需求编号使用PRD，任务使用M阶段或A1编号，质量用例使用QA，完整场景使用SCN，聚焦视觉/编辑验证的小样板使用VIS。它们分别代表用户价值、开发工作、验证证据和固定内容，不互相代替。样例中的H/D/N短编号仅是测试别名，实际实体仍使用稳定ID。

## 共同术语

| 术语 | 含义 |
|---|---|
| GM / 主持人 | 制作和持有完整工程的人，可访问秘密和线索 |
| 玩家投影 | 只含玩家可见内容的临时渲染数据，首版输出为PNG |
| SceneDocument | 完整可编辑场景的持久化模型，格式与渲染引擎独立 |
| revision | 文档成功事务的单调序号，撤销后也不会倒退 |
| editLocked / locked | 前者禁止编辑；后者是门窗通行锁，二者独立 |
| required | 房间必须有从指定入口出发的结构连接；不等于门当下敞开 |
| CommandBatch | 一次完整、可校验、原子提交和撤销的编辑批次 |
| Proposal | 尚待本机校验及主持人采用的AI建议 |
| 本地优先 | 核心数据与编辑在本地；不自动表示已经完成PWA离线冷启动 |
| 材质 / 主题 | 表面外观与协调的视觉规范；不替代通行、占地或秘密属性 |
| 组合组件 | 固定定义版本及已展开成员组成的可编辑物件组合；可拆开，不自动跟随定义升级 |
| 散布 | 受区域、密度、间距与排除条件控制的物件放置；完整保存采用结果和人工覆盖 |
| 离散高差 | 同一逻辑Floor内地面的高度差；不同于绘制顺序，不代表支持上下重叠的可行走楼层 |
